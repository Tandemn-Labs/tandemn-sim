# KoiBench Benchmark and Job Contract

Schema version: `koibench/v1`

This document is the canonical contract shared by every benchmark. A benchmark
is a collection of jobs. Each `benchmarks/<benchmark-id>/benchmark.md` file is
the human-readable source manifest; production tooling should parse its fenced
JSON events into a normalized JSONL or database representation before
execution.

## Time Model

| Field | Meaning |
|---|---|
| `submit_at_offset_minutes` | exact release time relative to benchmark start |
| `active_start_at_offset_minutes` | first instant at which an online generator may send traffic |
| `active_end_at_offset_minutes` | exclusive endpoint; no new request starts at or after this offset |
| `deadline_at_offset_minutes` | absolute batch deadline relative to benchmark start |
| `duration_minutes` | consistency check equal to active end minus active start |

Job arrivals are dispatched exactly, including off-tick arrivals. An arrival invokes the admission path immediately. The 5-minute tick is the slow reoptimization cadence, not the only admission opportunity.

Every run has a drain period after the offered-work horizon. The drain does not change deadlines. It exists to measure tardiness and in-flight completion. Work unfinished at its deadline is a deadline miss even if it finishes during drain.

## Job Definition and Runtime Separation

The benchmark manifest records offered jobs. Runtime state is written
separately.

Valid runtime states:

`queued`, `accepted`, `rejected`, `starting`, `running`, `draining`, `succeeded`, `failed`, `canceled`

Runtime timestamps:

| Timestamp | Meaning |
|---|---|
| `accepted_at` | irreversible admission decision |
| `ready_at` | first healthy online replica or first runnable batch shard |
| `started_at` | first useful execution |
| `completed_at` | successful completion only |
| `terminal_at` | success, failure, rejection, or cancellation |

`finished_at` is not used because it conflates successful completion with failure/cancellation.

## Online Job Contract

Online active windows are half-open: `[active_start, active_end)`.

Online work is generated by an external HTTP load generator. It sends OpenAI-compatible requests to `/v1/chat/completions`, `/v1/embeddings`, or `/v1/rerank`. `prompt_dataset_id` selects request payloads; it does not turn the online job into a batch campaign.

Required online `input_source`:

```json
{
  "type": "api_load_generator",
  "protocol": "openai_compatible_http",
  "endpoint": "/v1/chat/completions",
  "prompt_dataset_id": "immutable-payload-corpus",
  "profile_id": "poisson_mmp_bursty",
  "seed": 101
}
```

At `active_end_at_offset_minutes`:

1. Stop generating new requests.
2. Drain requests already admitted by the router.
3. Stop the service after the drain timeout or after all requests finish.
4. Record request outcomes and `terminal_at`.

Operations:

| Operation | Meaning |
|---|---|
| `base_service` | independently offered persistent API stream |
| `additive_stream` | additional demand that overlaps a base service |
| `replace_service` | replacement rollout; must identify the superseded service in executable manifests |

Overlapping `base_service` and `additive_stream` traffic is additive. A model swap is not additive after its cutover point; executable manifests must set `supersedes_job_id` and a cutover offset.

## Traffic Profiles

All current timing files are synthetic profiles intended for simulation or replay on real hardware. They are not production traces.

The production submitter supports exactly four traffic patterns. The manifests use no other traffic-pattern enum.

| `request_arrival_pattern` | Load-Generator Behavior |
|---|---|
| `Constant` | maintain the declared target concurrency throughout the active window |
| `Poisson` | stochastic API arrivals capped by the declared maximum concurrency |
| `Bursty` | alternating low/high concurrency windows, with `peak_to_mean_ratio >= 3` |
| `Diurnal` | sinusoidal concurrency envelope whose maximum equals the declared concurrency |

Business ramps, launch spikes, heavy-tailed bursts, and regime changes are scenarios implemented within `Bursty` or `Diurnal`; they are not additional submitter pattern names.

Traffic intent is mutually exclusive exactly as in `submit_job.py`:

| Field | Meaning |
|---|---|
| `max_concurrent_streaming` | sole authoritative online traffic input in these manifests; maximum active streaming requests |
| `request_arrival_rate` | omitted from submitted specs; Orca derives it from concurrency and target service time |
| `_traffic_mode` | set by Orca to `concurrency` |

`max_concurrent_streaming` is concurrency, not requests per second. The API generator and surrogate never exceed it. Orca derives an equivalent request rate as `concurrency / target_service_time`. Do not submit both concurrency and request rate.

Request token lengths use the submitter's accepted `isl_*` and `osl_*` fields and distribution names. Embeddings and rerankers use end-to-end latency for evaluation; a positive 1 ms TPOT compatibility value is submitted because the current online validator requires positive TPOT/OSL.

## Batch Campaign Contract

Every batch campaign expands deterministically because `expansion_policy` is `required`.

Batch work never uses RPS or an online API load generator. The executor reads a finite dataset, partitions it into logical shards, and writes results to `output_target`.

Required batch `input_source`:

```json
{
  "type": "dataset",
  "dataset_id": "immutable-dataset-id",
  "partitioning": "fixed_shards",
  "shard_count": 80,
  "requests_per_shard": 200
}
```

| Field | Meaning |
|---|---|
| `campaign_id` | stable parent identifier |
| `shard_count` | number of logical shards |
| `requests_per_shard` | logical requests in each shard |
| `checkpointable` | whether a stopped attempt can resume from saved progress |

Shard IDs are `campaign_id/shard-{index}`. Attempts are `shard_id/attempt-{index}`. Retries never increase logical shard count.

A campaign succeeds only when all required logical shards succeed. Campaign completion is the maximum successful shard completion timestamp. If any required shard permanently fails, `completed_at` is null and `terminal_at` records campaign failure.

## Planner-Fair Input

The planner does not receive descriptions, trace/dataset names, human-readable tenant names, expected mechanism labels, or preferred accelerators. It receives only:

- sanitized job and tenant IDs
- model and request-shape metadata
- explicit SLO/deadline/priority/quality constraints
- cluster/resource state
- the same performance interface and telemetry permitted by the experimental condition

Placement hints such as `preferred_accelerators` and `market_preference` are forbidden in job inputs. Backend/model compatibility comes from a separate, frozen compatibility manifest shared by every baseline.

## Quality and Quantization

Quantization, engine, LMCache, TP/PP/DP/EP, and accelerator choices are deliberately absent from submitted job specs because the submitter does not accept them as user-owned job fields. They live in a frozen planner candidate/compatibility manifest shared by every baseline. Before a quantized config enters that catalog, it must pass a task-specific non-inferiority gate.

FP4 is excluded unless the selected backend/device implements and validates the exact format. FP32 is calibration-only.

## Real-Run Load Calibration

Absolute concurrency cannot be declared feasible from accelerator count alone. Before opening the sealed test trace:

1. Profile each admitted model/config/device family on isolated hardware.
2. Build an independent capacity estimate unavailable to planners.
3. Select one global multiplier for `max_concurrent_streaming` per benchmark duration.
4. Target 55-65% qualified capacity in normal periods, 80-90% at ordinary peaks, and 105-120% only in the designated overload event.
5. Freeze the multiplier for every system and seed.

The listed concurrency values preserve relative tenant/job scale. The frozen global multiplier establishes absolute real-cluster load.

## Execution Validation

Before each run, reject a manifest unless all checks pass:

- all event, job, service, campaign, and shard IDs are unique
- active end equals release plus duration
- online windows stay within the offered-work horizon
- batch deadlines are at or after release
- requested models fit at least one frozen compatible configuration
- all TP/PP/EP combinations are physically legal
- expected counts equal parsed counts
- every submitted `job_features` key is accepted by `submit_job.py`
- online specs contain `max_concurrent_streaming` but not `request_arrival_rate`
- traffic pattern is one of `Poisson`, `Constant`, `Bursty`, or `Diurnal`
- no placement hints are visible to planners
